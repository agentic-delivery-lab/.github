# Contributing

Thank you for contributing to a repository in the agentic-delivery-lab
organization. These guidelines describe the organization-wide baseline. A
repository's own documentation and contribution files may add or override
instructions for that repository.

## Start with the repository

Read the target repository's README, contribution guide, security policy, and
other documented instructions before making a change. Follow its supported
toolchain, branch workflow, review process, and release rules. If local
instructions conflict with this default guidance, the repository-specific
instructions apply.

## Choose an issue path

Use the issue form that best describes the work. The organization provides
forms for ideas, research, features, bugs, tasks, requirements, architecture
decisions, implementation, and validation. If no form fits or the work is not
yet clear, use the enabled blank-issue option and explain what needs to be
understood.

Issue forms collect enough context for maintainers and contributors to assess
the request. They do not by themselves authorize implementation. Link related
issues, pull requests, decisions, documentation, and evidence when that helps
others understand the work.

## Submit safely

- Do not include passwords, API keys, private keys, access tokens, personal
  data, or other secrets in issues, pull requests, logs, screenshots, or
  patches.
- Remove or replace sensitive values before sharing diagnostic output.
- Submit only content that you are authorized to share.
- Report suspected vulnerabilities through the process in
  [`SECURITY.md`](SECURITY.md), not through a public issue or pull request.
- Follow the [Code of Conduct](CODE_OF_CONDUCT.md) in every project space.

## Open a pull request

Use the pull-request template to describe the change clearly. Include:

- a concise summary of what changed and why;
- links to the related issue or other work;
- the tests or checks you ran and their results;
- documentation changes or an explanation of why none are needed;
- security and privacy considerations;
- any breaking changes or compatibility concerns; and
- risks, trade-offs, follow-up work, or specific reviewer questions.

Follow the target repository's rules for branch names, commit messages, pull-
request bases, approvals, merge methods, and changelog entries. Keep a pull
request focused on one coherent outcome and update it when the scope changes.

## Test and document the change

Run the checks documented by the target repository before requesting review.
Add or update tests when behavior changes, and include useful failure output
when a check cannot run in your environment. Update user-facing and
maintainer-facing documentation when the change affects behavior, setup,
operations, security, or contribution steps.

## Review and merge

Reviewers consider scope, correctness, security, privacy, accessibility where
relevant, documentation, tests, compatibility, and maintainability. Explain
questions with evidence and keep feedback focused on the change. Maintainers
decide when the repository's required checks and review conditions are met.

For questions about using a project, see [`SUPPORT.md`](SUPPORT.md). For
security concerns, follow [`SECURITY.md`](SECURITY.md).
